# CodeNode Agent 不足与生产成熟度审阅

审阅日期：2026-09-13  
审阅基线：提交 1f633d640ee0a8847e472e832b68379c0b1ab6c1，分支 n0_12；本轮开始时工作区干净。  
范围：单用户桌面 Agent 的可靠性、安全性、运行恢复与评测。不是多租户云平台设计。

## 结论与此前判断修正

目前项目有实际工程价值：流式工具循环、角色工具隔离、本地检索、后台任务、取消信号以及自动化测试都已实现。但不能仅凭这些能力和名为 production-gate 的脚本，就认定生产门槛已经补齐。

此前“已经达到单机桌面可生产发布标准”“唯一缺少真实供应商测试”的判断不充分，应撤回。当前更合适的定位是：具备工程化基础、仍需可靠性和安全性加固的桌面 Agent 原型/Beta 候选。

此前真实供应商测试 PASS 证明了当时的模型接口可调用并能返回指定文本，不证明多步任务成功率、工具权限安全、恢复能力或长期稳定性。本文依据代码审阅；未重新运行真实模型、攻击测试或远程 CI，不将静态发现写成已复现事故。

## 优先级总览

| 优先级 | 不足 | 主要影响 |
| --- | --- | --- |
| P0 发布前 | 密钥可退回 Base64 保存 | 不能保证凭据静态加密 |
| P0 发布前 | shell/扩展没有操作系统资源隔离 | 可能越过项目边界产生副作用 |
| P0 发布前 | SSRF 校验与真实连接未绑定 | 私网访问边界不完整 |
| P1 | 事件记录不等于崩溃续跑 | 中断后无法可靠恢复任务 |
| P1 | token 预算缺少全任务统一记账 | 子代理、压缩调用成本不可控 |
| P1 | 取消与错误语义不完整 | 停止后仍可能残留进程或副作用 |
| P1 | 日志轮转与恢复有数据可靠性问题 | 可能丢失事件或错误标记运行 |
| P1 | 测试范围不足以证明生产可用 | 关键故障路径未被验证 |
| P2 | 检索、上下文、可观测性需改进 | 长任务质量、成本和定位效率受限 |

P0 指应阻止面向不可信项目的广泛发布，不代表已发现实际泄露。

## 1. 密钥保护仍会失效

证据：electron/modelStore.cjs 的 encryptSecret 在 safeStorage 不可用或加密失败时返回 plain:v1 加 Base64；decryptSecret 解密失败返回空字符串。

Base64 可直接还原，不能算加密。当前“文件不包含原始 Key”的测试只验证字符串被改变，无法证明保密性。解密失败静默变为空值，也可能让后续保存覆盖原来的加密凭据。

建议：安全存储不可用时拒绝持久化密钥，支持明确的仅内存模式；解密失败应保留原始密文并报告错误。旧明文配置迁移需要明确结果和恢复策略。

验收：安全存储不可用时无可逆弱编码落盘；模拟解密失败后编辑其他模型不丢失原密文；使用实际 Electron 安全存储验证迁移与重启读取。

## 2. shell 和扩展权限不是强隔离

证据：electron/tools/impl/executeShellTool.cjs 使用命令白名单和关键词判断；electron/tools/extensions.cjs 使用子进程、cwd 和环境变量过滤。

项目工作目录只决定相对路径的起点，不限制进程访问范围。允许解释器或构建脚本，也意味着允许它们执行任意程序逻辑。工具白名单、确认弹窗、环境变量过滤均不能替代文件系统和网络隔离。

扩展环境还直接继承所有 CODENODE_ 前缀变量，可能把同前缀的测试密钥传给扩展。应避免前缀通配放行，NODE_PATH 等加载相关变量也应审慎处理。

建议：建立独立的执行服务和明确资源策略，约束可读写目录、网络、进程数及输出容量；对桌面本机高权限模式明确展示边界；统一处理工具、工作流命令和扩展的审批策略。

验收：使用临时沙箱中的合成数据测试越界读写、外联、子进程和解释器执行；拒绝路径实际无副作用，而非只返回一个拒绝字符串。

## 3. SSRF 和联网资源限制仍有缺口

证据：electron/tools/impl/fetchUrlTool.cjs。

- 先 dns.lookup，再 fetch 原域名，真实连接可能重新解析；没有绑定已校验地址，存在 DNS 重绑定风险。
- IPv6 检查是字符串前缀判断，未完整处理 IPv4 映射 IPv6 等形式。
- 用字符正则判断“像 IP 的主机名”并跳过解析，不是严格的 IP 类型识别。
- 在 res.text 读取正文之前清除超时；慢正文可能超出预期时限。
- maxChars 是完整读取后的显示截断，不能限制下载量和内存。
- 未接入主 Agent 的取消信号。

建议：严格解析地址、绑定连接目标、逐跳验证重定向；超时覆盖 DNS、连接和正文；流式限制下载字节数并取消多余响应。

验收：用受控网络夹具验证私网、映射地址、重定向、解析变化、慢正文、超大正文和取消行为。不要访问真实内网敏感服务验证漏洞。

## 4. 当前 Run 日志不能支持可靠续跑

证据：electron/runStore.cjs 的 startRun、finishRun、recoverInterrupted 和 electron/main.cjs 中的接入。

日志记录生命周期和摘要，没有完整的执行检查点、待执行调用、调用结果提交状态及恢复入口。把状态标成 interrupted 仅能识别未完成记录，不能恢复任务。

此外，summarizeRun 将所有有开始但无结束的 Run 都视为 interrupted；recoverInterrupted 在新请求开始时调用，却不核对 activeRequests。因此一个仍在执行的 Run 也可能被写入恢复标记。

建议：采用持久化状态机，保留工具执行前后状态、消息和输出引用；启动恢复时识别真正失活的运行。对崩溃时结果未知的写操作，必须人工确认或通过幂等查询核对，不盲目重放。

验收：在模型请求前、工具执行中、文件修改后但状态提交前分别终止进程；重启能区分可续跑、需核对和已完成，且不重复副作用。

## 5. 预算与并发控制还不完整

证据：electron/agent.cjs 中 runAgentChat 的 usage 汇总和预算判断；electron/subagents.cjs 的独立运行；electron/main.cjs 的 activeRequests。

预算是在模型响应之后检查，单次请求可超额；依赖供应商 total_tokens 字段，缺失时没有可靠的保守限制。子代理和压缩请求未共享父任务的统一成本账本。并发上限只覆盖主请求，不等价于所有模型调用的全局队列。

建议：共享 Run 预算、请求前预留额度、响应后结算；统一累计主模型、压缩、子代理和嵌入成本；加入请求速率和有界队列。不要自动切换到不同数据供应商，除非用户已配置并接受。

验收：多子任务同时请求也不突破约定额度；无 usage、429、排队取消、最大输出预留均有行为测试。

## 6. 停止、失败与完成需要更严格语义

取消信号已传播，但 shell 主要终止直接子进程，未证明整棵进程树被清理。扩展取消、审批等待、压缩调用和联网正文的生命周期还需统一。

主循环触达迭代上限后仍可能进入 done；任务没有 error 并不意味着验收条件已满足。模型“说完成”不能作为完成判据。

建议：统一 completed、failed、cancelled、budget_exceeded、needs_review 等结束原因；工具失败区分业务失败、权限拒绝和可重试错误。禁止把权限拒绝包装成“换个命令继续”的普通失败。

验收：停止后不再启动新工具；进程树真实退出；已发生的修改可见；达到上限明确标为未完成；成功状态由任务验收支撑。

## 7. 日志系统仍有可靠性和隐私问题

证据：electron/runStore.cjs 的 appendJsonl/readRun；electron/main.cjs 的 runStore 事件写入。

2MB 只是触发阈值，保留最多 3999 行不保证文件降到 2MB 以下；单行也可能很大。轮转先删除旧文件再 rename，新文件替换前崩溃可能丢失日志。任意一行 JSON 损坏会让 readRun 返回空数组，丢掉其他可读记录。

Run 的 prompt 和 audit 直接写入事件日志，没有统一经过 agent.redactSecrets。原有日志脱敏又将包含 token 的统计字段也替换，可能损坏观测数据。日志目录文件总量没有保留上限。

建议：事件元数据与正文分离，统一脱敏入口和统计字段保留规则；耐受不完整尾行；原子保存关键状态；设置字节级与时间级保留策略。持久化失败不能全部静默忽略。

验收：故障注入覆盖磁盘满、断电窗口、损坏尾行和超大事件；日志无合成密钥原文，token 统计仍可计算。

## 8. 当前评测和 CI 不足以证明生产质量

证据：scripts/production-gate.cjs 主要检查源码模式与少量函数行为；scripts/provider-smoke.cjs 只要求模型返回固定文本；.github/workflows/production-gate.yml 仅配置 Ubuntu job。

当前缺少真实多步工具任务、修改后测试、长上下文、提示注入、取消和崩溃恢复的端到端评测。供应商脚本无 Key 时以成功退出码跳过，CI 启用后若漏配 Key 也可能形成假绿。

新增 workflow 中 npm run build 会触发 Electron 图标脚本，无显示环境下是否可运行需要实际 CI 证据。本轮未读取远程 Actions 结果，不能声称 CI 已通过。签名、升级和回滚也未提供验收证据。

建议：建立固定任务集，统计任务成功率、引用正确率、违规副作用、延迟与成本；发布模式缺少必需凭据应失败；验证 Windows/macOS/Linux 矩阵及安装、升级、回滚。

验收：报告绑定提交、模型、参数和数据集版本；标出失败与跳过；CI 实际运行成功，发布包经过目标平台验证。

## 9. 检索与上下文能力还需实测

默认哈希向量不等于学习型语义嵌入；BM25 候选预筛限制纯语义召回。引用白名单只能验证引用出现过，不能证明回答被引用内容支持。

建议为源码符号、中文描述、跨文件逻辑建立检索评测；验证文件变更后的向量缓存失效。长对话应有上下文预算和证据保留机制，压缩后不能只保留结论而丢掉来源。

验收：比较 BM25、哈希向量和学习型嵌入的检索效果、时延及成本；用已知正确答案评测，不能只凭演示观感选方案。

## 建议实施顺序

1. 先修凭据弱回退、执行权限边界、联网校验与正文资源限制。
2. 再修任务状态机、真正续跑、取消进程树与日志可靠性。
3. 建立统一预算/队列，以及可查询的运行指标与失败告警。
4. 最后以真实任务集和多平台发布测试验证，形成可复核的发布报告。

不建议继续凭“新增了多少功能”给出生产准备度百分比。生产成熟度应由明确场景、风险边界、失败处理和真实运行证据决定。上述问题并不否定项目的简历价值；能解释这些边界、修复过程及验证方法，本身就是有价值的工程能力。
