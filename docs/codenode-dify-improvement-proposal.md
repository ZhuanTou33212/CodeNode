# CodeNode 相对 Dify 的差异化改进建议

> 2026-10-01；范围：产品与架构建议，不代表下列功能已经实现。

## 1. 定位

**CodeNode 应专注“本地工程中的 Agent 工作台”**：让用户在同一个项目里完成“定位代码与画布数据 → 制定步骤 → 执行工具 → 审查修改 → 继续或恢复任务”。Dify 则主要提供构建、发布和运营 AI 应用的通用平台。两者都使用工作流、Agent、工具和 RAG，但服务的核心场景不同。

现有基础已经包括 Electron 桌面工作台、`.cnode` 画布、DAG 运行、Agent 工具循环与恢复，以及面向项目文件的 RAG。RAG 默认使用本地 BM25、标量查询和轻量向量层；语义嵌入、重排、SQLite 或 Milvus 均按需配置。任务轨迹和文件写入前后摘要已有首版，下面的 P0 建议聚焦跨视图关联和人工审查闭环。

## 2. 优先级总览

| 优先级 | 改进方向 | 用户得到什么 | 主要改动面 |
| --- | --- | --- | --- |
| P0 | 工程任务的可审查闭环 | 知道 Agent 为什么找到这些代码、改了什么、下一步会做什么 | 对话、检索结果、Diff、运行记录 |
| P1 | RAG 配置与检索依据可视化 | 轻量模式开箱即用；需要语义召回时能明确启用、诊断和回退 | RAG 设置、检索卡片、索引状态 |
| P1 | 画布节点执行契约 | 工作流更容易复用、定位失败节点和从中断处继续 | 节点配置、输入输出、运行状态 |
| P2 | 可选 Dify 互通 | 在确有应用发布或团队协作需求时复用 Dify 能力 | HTTP 工具适配、凭据和结果映射 |

### P0：把一次工程任务做成可审查的闭环

现有系统已有文件检索、工具执行、画布编辑、运行状态和 Diff。下一步应把这些信息串成一条用户能检查的任务轨迹：

1. **定位**：显示命中的文件、行号、符号、匹配方式（词法／向量／关系扩展）和检索范围；“匹配度”只表示检索相关性，不等同于答案已获事实支持。
2. **计划与执行**：在同一任务视图中关联画布节点、工具调用、等待确认、失败原因和恢复入口，避免用户在聊天、画布和日志之间猜测当前进度。
3. **审查修改**：文件写入和画布变更提供修改前后差异、来源与执行者；用户可以定位到具体文件或节点，再决定继续、调整或撤销。
4. **交付结果**：结束时输出“完成的步骤、实际改动、执行过的检查、未完成项”，并链接到对应证据。

**验收口径**：选一个真实项目任务，从提问到修改完成，用户无需打开原始日志即可找到每条关键结论的来源、每次写入的差异，以及任务停在何处。先做少量人工走查；暂不新建独立评测集。

### P1：让 RAG 的轻量默认和语义升级都可理解

保留当前默认：`rag.embed_provider=local`、`rag.vector_store=memory`，无需模型下载或外部服务。界面应明确说明本地哈希向量主要利用词项重合，不能称为真正的跨表达语义检索。

- **基础模式**：自动使用 BM25、标量查询和已实现的代码结构／关系检索；用户只需选择项目范围。
- **语义模式**：用户主动选择 Ollama 或 OpenAI 兼容嵌入服务；保存前检查端点、模型、维度与可达性，并提示索引重建的范围和成本。
- **存储选择**：小工程保持内存默认；需要跨会话保留向量时选择 SQLite；确有外部集群需求时再配置 Milvus。
- **结果解释**：展示检索来源、命中原因、引用范围、索引更新时间和降级原因。向量服务或重排服务失败时继续给出 BM25 结果，并明确标记降级。
- **隐私提示**：只有用户配置外部嵌入或重排端点时，才向该端点发送查询或候选内容；设置页应说明发送内容。

**验收口径**：默认安装后不配置模型即可检索；启用语义模型后能看到状态和失败原因；关闭语义模式后可立即回到本地检索。切换模型或维度时，不应把旧向量静默当作新模型索引使用。

### P1：明确画布节点的执行契约

CodeNode 的画布已经可以按 DAG 推进任务，也有运行恢复能力。建议在节点层补齐用户可见的契约，而不是只依赖自由文本 Prompt：

- 为 `task`、`stage`、`tool` 定义清晰的输入、输出和完成条件；连线时提示缺失的输入。
- 为可写操作标注作用范围和需要的确认；在运行前显示可能改动的文件或画布对象。
- 节点运行记录保留输入摘要、输出引用、失败分类和重试次数，支持从失败节点继续。
- 把可复用链路保存为 `.cnode` 模板，并说明其依赖的工具、模型和项目路径；导入时检查缺失依赖。

**验收口径**：用户能判断一个节点为何阻塞、它消费了哪个上游结果、重跑会不会重复写入，以及模板换项目后哪些配置需要补齐。

### P2：把 Dify 当作可选集成端

若用户需要对外发布聊天应用、通用文档知识库或团队运营，可通过一个可选适配层调用已发布的 Dify 应用／工作流。建议先实现最小的 **CodeNode → Dify** 单向调用：配置服务地址和凭据、映射输入变量、展示输出与错误，并纳入 CodeNode 的工具权限和审计。不要让默认本地任务依赖 Dify 服务。

反向的 **Dify → CodeNode** 工程操作需要 CodeNode 新增受控的对外接口、身份验证与工程授权，属于单独项目；当前不应作为已具备的集成能力宣传。

**验收口径**：未配置 Dify 时现有工作流行为不变；配置后一次调用能清楚显示输入、输出、耗时及失败原因，且不会绕过本地写入确认。

## 3. 建议实施顺序

1. **完善 P0 的任务轨迹和修改审查**：在已有首版上关联检索引用、工具记录、Diff 与运行状态；优先消除“Agent 做了什么看不清”的体验问题。
2. **再做 P1 的 RAG 设置与状态展示**：把已经存在的轻量默认、可选语义后端和降级信息变成用户可理解的配置与反馈。
3. **随后完善画布节点契约**：从 `task`／`stage`／`tool` 的输入输出与失败恢复开始，逐步沉淀模板。
4. **最后按真实需求接 Dify**：只有出现应用发布或团队复用场景，再投入适配与维护成本。

## 4. 本阶段边界

- 不以复刻 Dify 的通用应用市场、多租户运营后台或托管服务为目标。
- 不把语义模型、外部向量库、重排服务或 Dify 服务变成安装后的必需依赖。
- 暂不建设独立 RAG 评测集；先通过现有回归检查和少量真实任务走查判断体验问题，待关键路径稳定后再决定评测范围。
