# Agent 模块问题核查与修复任务单

## 任务目标

请基于当前仓库实际代码，逐项核查下面的问题，区分：

1. 确认存在的缺陷；
2. 真实但属于能力缺口或性能债；
3. 设计取舍，不应误报为 bug；
4. 截图或静态搜索无法证明、需要补充证据的结论。

不要仅根据文件名、README 或一次 `grep` 结果下结论。每一项都要给出：

- 相关文件和准确行号；
- 触发条件；
- 用户可观察到的影响；
- 是否已有保护逻辑或测试；
- 建议优先级；
- 最小修复方案；
- 回归测试方案。

如果结论只是“没有某功能”，请明确写成“能力缺口”，不要直接写成“bug”。如果证据不足，请标记为“待核实”，不要猜测。

## 一、优先核查并优先修复

### 1. 工具结果导致上下文持续膨胀

现象线索：大量工具结果可能被直接追加到模型上下文；曾观察到约 40 次、每次约 27KB 的结果，累计输入约 434,743 字符，约 145k tokens。截图中还提到没有找到明确的 `estimateTokens` 使用点。

请核查：

- 工具结果进入模型前是否有 token 估算；
- 是否有总上下文预算、单工具结果预算和单轮预算；
- 超预算时是主动裁剪、摘要、截断，还是等模型 API 报错；
- `agent.max_total_tokens` 是事前预算还是事后硬限制；
- 图片、文件、MCP 返回值是否走同一套预算逻辑；
- 是否可能因为原始工具输出导致 UI、IPC 或序列化阻塞。

建议方向：建立统一的上下文预算器，在调用模型前完成预算检查；优先保留用户消息、最近工具结果和错误信息，对较旧或超大的结果做摘要/截断，并保留可追溯提示。

验收标准：构造连续大输出工具调用，模型请求不会无界增长；超预算时有明确、可测试的降级行为，而不是直接超窗失败。

优先级建议：P0/P1，最终根据生产模型上下文限制和实际失败率确定。

### 2. 达到最大迭代次数后的任务收尾

现象线索：达到 `agent.max_tool_iterations` 后返回“已达到模型迭代上限，任务未完成”一类错误，疑似没有总结当前进度、保存恢复点或提供续跑机制。

请核查：

- 达到工具调用上限时，是否仍会生成最终总结；
- 当前已完成的结果、失败原因和待办是否被保存；
- 用户是否可以从上次状态继续，而不是从头执行；
- 上限是防死循环的安全阀，还是被误当成普通错误；
- 是否已有外层重试、续跑或用户确认逻辑。

建议方向：到达上限后输出结构化收尾信息，包含已完成事项、未完成事项、失败原因和可继续执行的状态；不要无条件自动无限续跑。

验收标准：达到上限时用户能看到有用的阶段性结果，并能明确选择继续或结束；不能重复执行已经完成的破坏性操作。

优先级建议：P1。

### 3. 成本账本是否正确处理缓存 token

现象线索：`tokenParts` 似乎记录了 cached/miss，但 `costOf()` 可能只按照 input/output 总量计费。

请核查：

- 各模型/供应商的缓存输入价格是否与普通输入不同；
- 成本账本记录的是精确费用、估算费用，还是仅用于排序的内部指标；
- cached、input、output、reasoning token 是否被分别记录；
- UI 或日志是否把估算值展示成精确账单。

结论要求：

- 如果实际计费不同而账本忽略 cached 价格差异，确认是成本统计缺陷；
- 如果当前账本明确只是统一单价估算，说明精度限制即可，不要夸大为计费 bug。

验收标准：使用固定 token 账单样例验证计算结果；不同模型的价格配置有测试覆盖。

优先级建议：P1/P2，取决于该账本是否用于真实额度或费用展示。

### 4. 工具注册表、实现文件和文档漂移

现象线索：`create_nodes`、`workbench_connect` 似乎存在实现文件，但没有进入默认注册表；README 仍将它们列为工具。

请核查：

- 这些文件是废弃代码、实验代码、未发布功能，还是本应可用的工具；
- 默认注册表、描述符、side effect 声明、README、测试是否一致；
- 用户能否通过任何路径调用这些工具；
- 是否存在注册但实现缺失，或实现存在但能力声明缺失的情况。

处理要求：

- 若应发布：补齐注册、描述符、权限/副作用声明和测试；
- 若不应发布：移入明确的 experimental/legacy 区域，或清理过时文档；
- 不要仅为了让数量对上而注册未完成工具。

优先级建议：P2，若导致用户按照 README 调用失败，可提升为 P1。

## 二、需要确认产品定位后再处理

### 5. 记忆是否只有最近切片，没有检索

现象线索：可能存在类似 `memory.entries.slice(-30)` 的注入逻辑，key/tag 没有参与检索。

请先确认产品契约：当前 memory 是“最近事件记忆”，还是“可检索的长期用户记忆”。

- 如果契约是长期记忆：需要按项目、用户、key/tag 或语义检索，并补充隐私、删除和可解释性机制；
- 如果契约只是最近记忆：不要把没有语义检索称为“只有写没有读”，应记录为功能范围限制；
- 跨项目用户级记忆和 UI 管理属于产品能力，除非已有明确需求，不要直接定性为 bug。

优先级建议：按产品需求决定，默认 P2 能力缺口。

### 6. 子代理的可见性、单任务取消和持久化

现象线索：子代理任务可能只保存在内存 `Map` 中，没有独立 UI、独立取消通道或重启后恢复。

请核查：

- 子代理是否是用户可见产品能力，还是内部并行实现；
- 是否有任务 ID、状态、进度、错误和结果查询接口；
- 是否可以只取消一个子任务，而不是取消整个 agent；
- 进程重启后是否需要恢复；
- 现有 `AbortSignal` 能否安全取消正在运行的工具调用。

结论要求：分别列出“缺 UI”“缺单任务取消”“缺持久化”，不要合并成一个笼统结论。

优先级建议：若子代理对用户可见，P1/P2；若仅为内部实现，按实际稳定性问题处理。

### 7. MCP 是否应该复用会话

现象线索：每次 MCP 调用可能执行 `spawn -> initialize -> tools/call -> kill`，没有复用长连接，也可能没有动态执行 `tools/list`。

请核查：

- MCP server 是否有启动成本；
- 是否依赖会话状态；
- 当前隔离式生命周期是否是为了可靠性和清理；
- 初始化失败、超时、崩溃时是否能正确回收；
- `tools/list`、`resources`、`prompts` 是否是当前产品必须支持的协议能力，还是可选能力。

不要直接把“没有 tools/list/resources/prompts”判定为 bug。只有在产品契约要求动态发现或会话状态时，才应提出对应修复。

优先级建议：先测量启动开销和可靠性，再决定是否做连接池/会话复用，默认 P2 性能优化。

### 8. 长会话全量回灌

现象线索：当前会话消息可能每次完整传给主进程/agent，没有“最近 N 轮”选项。

请区分：

- 模型为了理解会话而需要完整历史；
- UI/IPC 为了渲染或传输而重复序列化完整历史；
- 超长历史没有摘要、分页或 token 预算。

不要把“全量历史”本身直接判定为 bug。真正需要解决的是超长会话的 token、内存、序列化和响应时间问题，并且要和第 1 项避免重复统计。

优先级建议：与上下文预算一起评估，默认 P2。

### 9. 单文件同步读写阻塞主进程

现象线索：`read_file` / `edit_file` 可能仍使用同步文件操作，没有搬到 worker；大文件会占用主进程，且同步调用本身难以中断。

请核查：

- 同步操作具体在哪个进程/线程执行；
- 文件大小达到什么阈值会出现可观测卡顿；
- 是否有超时、大小限制、分块读写或取消检查；
- 搬到 worker 的通信开销是否会抵消收益；
- 是否已有性能测试或测量记录。

若确认大文件会阻塞 UI 或 IPC，建议增加大小阈值和 worker 路径；小文件可以保留快速路径。

优先级建议：P2/P3，按实测卡顿确定。

## 三、不要直接当成 bug 的结论

### 10. 没有每个工具独立 rate limit

全局并发限制、模型队列和工具超时已经存在时，没有每工具独立限流不等于缺陷。只有在以下场景成立时才需要补充：

- 某个工具会触发高成本或不可逆外部副作用；
- 某个工具可能被循环调用并拖垮系统；
- 安全/配额需求明确要求按工具隔离。

否则应记录为可选治理能力，而不是 P2 bug。

### 11. 压缩配额按请求数而不是按条数

`max_calls=8`、每批最多若干条，可能是有意限制压缩模型请求次数。压缩后仍有原文也可能是：

- 条目未达到压缩阈值；
- 压缩失败后的安全回退；
- 批次大小或 token 预算限制；
- 需要保留的原始信息。

请先读清楚 `shouldCompress`、批处理逻辑和失败回退，再判断是否违反契约。不能仅凭“40 条中 26 条被压缩”证明实现错误。
