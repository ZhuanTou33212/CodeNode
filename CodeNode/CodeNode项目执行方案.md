## 0. 本文档定位

本文档只描述 CodeNode 项目的第一步实施工作，不是完整产品的最终建设方案。

第一步的唯一发布形态是 **Codex 插件**。最终交付物必须是符合 Codex 插件规范、能够安装、启用、禁用、升级和卸载的插件目录或插件包，而不是独立桌面应用、普通 Web 网站或浏览器扩展。

第一步聚焦于打通 Java 最小闭环：在 Codex 中打开 CodeNode 节点界面，使用自然语言生成 Java 节点，连接节点，审查 Java 代码，调用本地 JDK/Maven 编译运行，并把错误定位回节点。多语言、独立客户端、云协作和插件市场运营属于后续步骤。

## 1. 项目目标

CodeNode 第一步产品是一个安装并运行在 Codex 中的可视化代码编排插件。用户通过类似 Unreal Engine Blueprint 的节点画布，用自然语言描述 Java 变量、逻辑或功能，由 Codex Agent 将描述转成结构化节点和可审查的 Java 代码，再调用本地 JDK/Maven 工具链编译、运行并定位错误。

项目的核心价值不是单纯“让 AI 写代码”，而是把 AI 生成、代码审查、依赖连接、编译运行、错误定位和代码复用放入一个可追踪的节点工作流中。

### 1.1 第一步 MVP 成功标准

MVP 必须完成一条可演示的闭环：

1. 用户创建自然语言节点。
2. Agent 将自然语言转换为结构化节点及独立代码块。
3. 用户连接节点，系统校验端口和依赖。
4. 系统生成项目说明 Markdown 和可执行代码。
5. 调用本地编译器或运行时执行代码。
6. 错误能映射回具体节点，节点标红，点击错误可回到节点。
7. 成功的节点链可封装为复用节点或导出为文件。
8. 功能以 Codex 插件包交付，可在目标 Codex 版本中完成安装、启用、升级和卸载验证。

### 1.2 第一步 MVP 范围控制

首版只支持 Java 和一套经过固定的构建环境。建议采用 Java 21 LTS + Maven，优先保证生成结果、依赖解析和编译诊断的可重复性；Gradle 作为后续适配项。前端仍可使用 TypeScript，但节点生成、代码分析、编译运行和项目导入均以 Java 为第一目标语言。

MVP 包含：

- Codex 插件清单、入口、配置和版本信息；
- Codex 内的 CodeNode 打开入口和插件生命周期处理；
- 节点画布、缩放、拖拽、连线和搜索；
- 空白自然语言节点、已有模板节点；
- 节点属性编辑与代码审查；
- Agent 结构化输出；
- 端口类型校验、拓扑排序、代码生成；
- 本地编译/运行和错误定位；
- 工作流保存、加载；
- 节点链封装和 JSON/Markdown/源代码导出；
- 小范围项目结构导入与分析。

MVP 暂不包含：

- 独立桌面版、普通 Web 版和浏览器扩展版；
- Java 以外的多语言、多编译器同时支持；
- 对任意大型项目进行完整“反编译”；
- 多人实时协作；
- 插件市场与云同步；
- 自动执行不受信任代码；
- 一次性生成完整生产级大型应用。

## 2. 已确定需求整理

### 2.1 界面结构

- 顶部工具栏：语言/代码类型切换、编译/运行、开始制作、封装输出、分析项目结构。
- 中央工作台：UE 风格网格背景，支持节点创建、移动、连接和定位。
- 右侧检查器：节点自然语言/参数编辑页、生成代码审查页。
- 底部错误栏：按“[节点名] / [错误信息]”展示，点击后聚焦对应节点。
- 快捷入口：`Shift + A` 打开“新建空白节点/搜索已有节点”菜单。

### 2.2 节点行为

- 空白节点接受自然语言，由 Agent 转换为合法节点。
- 已有节点是可复用的完整逻辑或封装代码，具有明确输入输出。
- 节点按类别着色，但不能只靠颜色表达类型。
- 节点名称在生成完成后由系统提炼，同时保留用户改名能力。
- 节点代码块应尽量独立，便于审查、测试和复用。

### 2.3 生成与执行

- Agent 分析全部节点文本、上下文和连接关系。
- 生成一份 Markdown 中间说明，记录每个节点的分析、依赖和预期输出。
- 将节点图转换为代码，并调用本地工具链编译或运行。
- 编译错误必须经过 source map 映射到节点，而不是只展示原始行号。

### 2.4 输出与导入

- 节点链可封装为一个新节点，并自动生成输入/输出端口。
- 工作流可导出为源代码或 JSON、TOML 等文件。
- 可导入部分项目文件，分析结构并生成节点；首版目标是“结构分析与节点化”，不是二进制反编译。

## 3. 产品与技术总体方案

### 3.1 推荐架构

```text
Codex 宿主
        │
        ▼
CodeNode 插件入口与生命周期
        │
        ▼
插件界面（节点画布、检查器、错误栏）
        │ IPC / 本地 HTTP
        ▼
本地编排服务
  ├─ 工作流存储
  ├─ Agent 适配器
  ├─ 节点校验与拓扑排序
  ├─ 代码生成器
  ├─ 编译/运行沙箱
  └─ 诊断映射器
        │
        ├────────► Agent API / 本地模型
        └────────► 本地编译器、运行时、文件系统
```

推荐技术栈：

- 发布载体：Codex 插件目录/插件包，包含插件清单、入口、资源和必要配置；
- UI：React + TypeScript；
- 节点画布：React Flow（先验证能力，再决定是否自研）；
- 状态管理：Zustand；
- 本地编排服务：Java 21；轻量本地 HTTP/IPC 服务优先，确需完整 Web 能力时再采用 Spring Boot；
- 数据校验：共享 JSON Schema；前端使用 Zod，Java 服务使用 Jackson + Bean Validation；
- Java 代码解析：JavaParser；需要更完整的 IDE 级语义分析时评估 Eclipse JDT；
- 构建与依赖：Maven Wrapper（`mvnw`），MVP 仅支持 Maven 项目；
- 编译诊断：优先使用 JDK Compiler API（`javax.tools.JavaCompiler`），项目级构建补充解析 Maven 输出；
- 持久化：工作区内 JSON 文件，后期再引入 SQLite；
- 测试：JUnit 5（Java 核心）+ Vitest（前端）+ Playwright（端到端）；
- 进程执行：受控 JVM/子进程，固定 JDK、classpath、工作目录、超时、输出上限和命令白名单。

### 3.2 核心数据模型

所有 Agent 输出必须先通过结构化协议进入系统，禁止直接把自由文本当作可执行代码运行。

```ts
type Workflow = {
  id: string;
  name: string;
  language: "java";
  nodes: CodeNode[];
  edges: Edge[];
  version: number;
};

type CodeNode = {
  id: string;
  name: string;
  category: "input" | "transform" | "control" | "output" | "custom";
  prompt: string;
  analysis: string;
  code: string;
  inputs: Port[];
  outputs: Port[];
  status: "draft" | "generating" | "ready" | "running" | "success" | "error";
};

type Port = {
  id: string;
  name: string;
  dataType: string;
  required: boolean;
};
```

边需要记录源节点、源端口、目标节点和目标端口。保存时执行 schema 校验和版本迁移，避免后续数据格式升级导致旧项目无法打开。

### 3.3 Agent 工作协议

每次生成分为“分析”和“落盘”两个阶段：

1. 收集当前节点、上游输出、下游约束、语言和项目规则。
2. 请求 Agent 返回 JSON：建议节点名、功能摘要、端口、代码、依赖、风险和测试样例。
3. 使用 JSON Schema 校验；失败时自动修复一次，仍失败则展示给用户确认。
4. 生成代码预览和差异，用户确认后写入工作区。
5. 为每段代码添加稳定的节点标记，供编译诊断反向映射。
6. 生成 `workflow-analysis.md`，作为可追踪的中间产物。

上下文只发送当前节点、直接依赖和必要的项目约束，避免全图无差别发送造成成本高、响应慢和上下文污染。

### 3.4 代码生成和错误映射

Java 代码生成器先对图进行以下检查：

- 是否存在环；
- 必填端口是否已连接；
- 输入输出类型是否兼容；
- 节点名称和变量名是否冲突；
- Maven 依赖、包名、导入和 classpath 是否缺失或冲突；
- 是否存在孤立但被要求执行的节点。

校验通过后按拓扑顺序拼装代码。每个节点优先生成独立 Java 方法；需要独立状态或生命周期时才生成类。系统统一管理包名、imports、类名、方法名、泛型与受检异常，并记录生成代码的起止行：

```json
{
  "node-17": { "file": "generated/src/main/java/codenode/generated/Main.java", "startLine": 24, "endLine": 38 }
}
```

`javac` 或 JDK Compiler API 返回源文件、行号、列号和诊断码后，诊断映射器查表得到节点 ID，在错误栏展示简化信息，同时保留“查看原始诊断”入口。运行时错误通过节点方法包装、Java 堆栈帧和行号映射采用相同机制定位。Maven 依赖解析失败属于项目级错误；能够归因到节点声明的依赖时再关联节点，避免错误定位失真。

### 3.5 安全边界

- 默认仅在临时工作目录执行生成代码；
- 默认使用指定的 JDK 和 Maven Wrapper，禁止调用来源不明的构建脚本；
- 编译和运行必须由用户主动触发；
- 对命令、环境变量、工作目录设置白名单；
- 设置执行超时、内存/输出上限并允许立即终止；
- 禁止默认访问用户密钥、浏览器凭据和工作区外文件；
- 涉及安装依赖、联网、删除或覆盖文件时必须二次确认；
- 导入项目时遵循 `.gitignore`，并默认排除 `.env`、密钥和大文件。

## 4. 分阶段制作步骤

## 阶段 0：Codex 插件能力验证与需求冻结（第 1 周）

### 制作步骤

1. 固定发布形态为 Codex 插件，确认目标 Codex 版本和插件规范。
2. 建立最小插件骨架，验证安装、启用、打开入口、配置读取、升级和卸载流程。
3. 验证 Codex 插件是否能承载节点画布，以及插件前端与本地 Java 编排服务的通信方式。
4. 明确插件可申请的文件、进程、网络和本地工具链权限；无法直接获得的能力必须通过受控本地服务实现。
5. 固定 Java 基线：Java 21 LTS、Maven Wrapper、UTF-8、JUnit 5，并明确 MVP 不支持 Gradle。
6. 制作低保真原型，包含工具栏、画布、右侧检查器、底部错误栏。
7. 验证 React Flow 是否满足快捷创建、端口类型、节点聚焦和千级节点性能要求。
8. 验证本地服务能通过 JDK Compiler API 编译、运行一个 Java 类，并获得结构化诊断。
9. 验证 Codex Agent 能稳定返回符合 schema 的节点 JSON。
10. 编写 3 个金丝雀用例：变量计算、条件分支、读取 JSON 后转换并输出。

### 交付物

- 产品需求说明和范围清单；
- 可安装的最小 Codex 插件骨架；
- Codex 插件能力与权限验证报告；
- 可点击原型；
- 技术验证代码；
- 节点、边、工作流 JSON Schema；
- 3 个端到端验收用例。

### 验收标准

- 插件可在目标 Codex 版本中安装、启用、打开和卸载；
- 团队明确 Codex 插件边界、Java 基线和第一步 MVP 范围；
- Agent 的结构化输出在 20 次测试中成功率不低于 90%；
- Java 编译错误能被程序解析为文件、行、列和诊断码；Maven 依赖错误能被归类为项目级诊断。

- `executable-workflow` 已冻结单节点/可达子图请求结构和 DSL 入口；Stage0 强制不编译、不运行，封装代码节点和完整程序转译留到后续阶段。

- 大型项目导入、千级业务节点性能优化及更完整的布局持久化。

## 阶段 1：节点编辑器基础（第 2～3 周）

### 制作步骤

1. 建立前端工程、路由、状态管理和基础主题。
2. 实现网格画布、缩放、平移、框选、节点拖拽和删除。
3. 实现 `Shift + A` 菜单：创建空白节点、搜索模板节点。
4. 实现带类型的输入/输出端口和连线规则。
5. 实现右侧双页签：需求描述、代码审查。
6. 实现节点状态和分类配色，并增加图标/文字标签保证可访问性。
7. 实现撤销/重做、自动保存、加载和崩溃恢复。
8. 增加单元测试和节点交互 E2E 测试。

### 验收标准

- 用户能完成节点增删改、连接、保存和重新打开；
- 非法端口连接被阻止并给出原因；
- 50 个节点下常规拖拽和缩放无明显卡顿；
- 刷新或意外关闭后最近一次自动保存可恢复。

## 阶段 2：Agent 节点生成（第 4 周）

### 制作步骤

1. 定义 Agent Provider 接口，隔离具体模型厂商。
2. 建立系统提示、上下文裁剪和结构化响应 schema。
3. 将空白节点的自然语言转换为名称、摘要、端口、代码和测试。
4. 在右侧代码页展示生成结果、差异和接受/重新生成按钮。
5. 将确认后的结果写回节点，同时保留上一版本用于回滚。
6. 汇总工作流生成 `workflow-analysis.md`。
7. 增加失败重试、取消、超时和令牌/耗时提示。

### 验收标准

- 3 个金丝雀用例均可生成结构合法的节点；
- Agent 无法直接绕过 schema 写文件或启动进程；
- 用户能看到并审查变化，能回滚到上一个版本；
- 生成的 Markdown 能说明各节点功能、上下文、依赖和预期效果。

## 阶段 3：代码生成、编译与错误定位（第 5～6 周）

### 制作步骤

1. 实现图校验：环检测、必填端口、类型兼容和孤立节点。
2. 实现拓扑排序和“节点到 Java 方法/类”的代码生成模板。
3. 生成标准 Maven 目录、`pom.xml`、入口类、包声明、imports 和节点行号映射文件。
4. 实现受控进程执行器及开始、停止、超时机制。
5. 解析 JDK Compiler API、`javac`、Maven 构建诊断和 Java 运行时堆栈。
6. 将错误映射为“节点名 / 错误信息”，节点标红。
7. 点击错误时缩放并居中到目标节点，自动打开代码页和相关行。
8. 为编译成功、类型错误、语法错误、缺少依赖、受检异常和运行时错误分别编写集成测试。

### 验收标准

- 合法工作流能生成并运行代码；
- 图级错误在编译前被发现；
- 编译和运行时错误均能准确定位节点；
- 用户能停止长时间运行的任务；
- 原始诊断完整保留，简化信息不掩盖关键原因。

## 阶段 4：封装、导出和项目分析（第 7～8 周）

### 制作步骤

1. 实现多节点选择及“封装为节点”。
2. 根据跨边界连线推导新节点的输入和输出端口。
3. 保存封装节点的版本、依赖和来源，加入模板库。
4. 实现导出：工作流 JSON、分析 Markdown、生成源代码。
5. 增加 JSON/TOML 文件输出节点；格式必须由 schema 或模板约束。
6. 实现项目导入向导：选择目录、预览排除项、确认扫描。
7. 通过 AST 分析目录、模块、函数和引用关系，生成只读节点图。
8. 允许用户选择部分分析结果转为可编辑节点，禁止无确认覆盖原代码。

### 验收标准

- 封装前后的 3 个金丝雀用例输出一致；
- 封装节点能再次拖入画布并正常连接；
- 导出文件可被重新导入；
- 项目分析明确标注“已识别”“推测”“不支持”，不会宣称完成任意反编译。

## 阶段 5：Codex 插件打包、稳定性与发布（第 9～10 周，可按资源压缩）

### 制作步骤

1. 完成错误恢复、日志脱敏、取消任务和异常兜底。
2. 对 100、500、1000 节点进行画布和保存性能测试。
3. 对恶意提示、命令注入、路径穿越和超大输出进行安全测试。
4. 完成新手引导、快捷键帮助、示例工作流和空状态页面。
5. 建立版本迁移、崩溃报告和可关闭的匿名指标。
6. 按 Codex 插件规范生成版本化测试包，校验插件清单、入口、资源、权限声明和依赖完整性。
7. 在干净 Codex 环境执行安装、首次启动、升级、禁用、重新启用和卸载测试。
8. 邀请 5～10 名目标用户通过 Codex 安装测试插件并完成统一任务。
9. 修复阻断问题后发布第一步 MVP 插件包，并保留功能开关便于回滚。

### 发布门槛

- 交付物是可安装的 Codex 插件包，不依赖开发仓库才能启动；
- 插件清单、版本、入口、配置、资源和权限声明完整；
- 在声明支持的 Codex 版本中通过安装、启用、升级、禁用和卸载测试；
- 核心 E2E 用例全部通过；
- 不存在未处理的高危安全问题和数据丢失问题；
- 新用户在不看开发文档的情况下能完成一次生成、运行和错误定位；
- 工作流格式带版本号，升级后旧文件可迁移或只读打开。

## 7. 可能遇到的问题与应对

### 7.1 Agent 输出不稳定

问题：自由文本难以解析，节点端口或代码格式可能缺失。  
应对：强制 JSON Schema；低温度；失败自动修复一次；生成前后均做静态校验；无法修复时禁止执行并交给用户确认。

### 7.2 节点独立性与整体代码冲突

问题：完全独立的代码块可能重复定义、引入冲突或无法共享状态。  
应对：节点输出独立函数和显式端口；公共依赖由生成器统一注入；禁止节点隐式访问全局变量；通过 IR（中间表示）拼装，而不是简单字符串连接。

### 7.3 错误无法准确映射节点

问题：代码格式化、转译或打包会改变行号。  
应对：保留节点标记和 source map；MVP 禁止在诊断前二次压缩；编译错误用生成文件映射，运行错误用 source map + 堆栈解析。

### 7.4 图规模扩大后性能下降

问题：大量节点导致渲染、自动保存和上下文组装卡顿。  
应对：视口虚拟化、增量保存、状态切片、只重算受影响子图；Agent 只接收局部依赖上下文；建立 100/500/1000 节点性能基线。

### 7.5 任意代码执行带来安全风险

问题：生成代码可能删除文件、泄露密钥、联网或长期占用资源。  
应对：临时目录、最小权限、命令白名单、超时与资源上限；敏感操作单独授权；生产版优先使用容器或系统级沙箱。

### 7.6 “分析项目结构”范围失控

问题：源代码结构分析与二进制反编译完全不同，后者成本和法律风险高。  
应对：MVP 仅解析受支持语言的源文件和配置；界面明确能力边界；大项目采用目录筛选和增量索引；不承诺还原不可见源码。

### 7.7 多语言抽象过早

问题：即使只支持 Java，Maven/Gradle、不同 JDK、模块系统、注解处理器和框架也会带来明显差异。  
应对：MVP 固定 Java 21 + Maven，优先支持普通 Java/JUnit 项目；Spring、Android、Java Platform Module System 和注解处理器项目先标记为受限支持。Java 路径稳定后再抽象 `LanguageAdapter`，包含解析、生成、格式化、依赖解析、编译、运行和诊断七个接口。

### 7.8 封装节点后行为改变

问题：外部依赖、隐式变量或执行顺序可能在封装后丢失。  
应对：封装前检查跨边界依赖；自动推导端口；保存来源图；封装前后运行同一组测试并比较输出。

### 7.9 颜色分类影响可访问性

问题：只靠颜色区分节点，对色弱用户无效。  
应对：颜色、图标、类别文字同时使用；确保对比度；提供高对比主题。

### 7.10 用户误以为生成代码可靠

问题：AI 生成结果可能能编译但逻辑错误。  
应对：默认显示代码与测试；高风险操作必须确认；节点状态区分“已生成、已编译、已测试”；不得把编译成功等同于功能正确。

## 8. 测试与验收方案

### 8.1 测试层级

- 单元测试：schema、图校验、拓扑排序、Java 类型/泛型端口、imports、异常传播、诊断映射、版本迁移；
- 集成测试：Agent 响应到节点、节点图到代码、代码到编译诊断；
- E2E 测试：创建节点、连线、生成、审查、执行、定位错误、封装和导出；
- 安全测试：命令注入、路径穿越、敏感文件读取、依赖安装和无限输出；
- 性能测试：大图交互、保存、加载、生成和项目扫描；
- 用户验收：新用户完成规定任务并记录时间、失败点和求助次数。

### 8.2 必测业务场景

1. 两个数值输入经过计算节点输出结果。
2. 输入为空时，必填端口校验阻止运行。
3. 两节点互相连接形成环，系统指出环路节点。
4. Agent 返回不合法 JSON，系统修复或安全失败。
5. 生成的 Java 代码存在类型、包名、import 或受检异常错误，错误栏定位正确节点。
6. 运行时抛出异常，点击错误回到节点和代码行。
7. 多节点封装后输入输出与封装前一致。
8. 关闭并重新打开应用，工作流和节点版本不丢失。
9. 导入包含 `.env` 的项目，默认不读取敏感文件。
10. 长时间任务能被取消，且不会遗留后台进程。

## 9. 项目管理与质量机制

### 9.1 每周节奏

- 周一：确定本周可演示目标和验收标准；
- 每日：围绕阻塞项进行 15 分钟同步；
- 周中：合并一次可运行主干，避免长期分支；
- 周五：端到端演示，不以代码完成度代替产品闭环；
- 演示后：更新风险清单、性能指标和下周范围。

### 9.2 完成定义（Definition of Done）

一个功能只有同时满足以下条件才算完成：

- 需求和异常路径已实现；
- 有对应自动化测试；
- 错误信息对用户可理解；
- 不会绕过权限或安全确认；
- 数据可保存并兼容版本；
- 已在端到端演示中通过验收；
- 文档和示例已更新。

### 9.3 核心指标

- 首次成功闭环率；
- 从输入描述到可运行结果的中位耗时；
- Agent 结构化输出一次通过率；
- 错误到节点映射准确率；
- 崩溃恢复成功率；
- 用户接受生成结果前的平均修改次数；
- 封装节点的复用次数。

## 10. 建议目录结构

```text
CodeNode/
├─ .codex-plugin/              # Codex 插件清单与发布元数据
│  └─ plugin.json
├─ plugin/                     # Codex 插件入口、生命周期和配置
│  ├─ src/
│  └─ assets/
├─ apps/
│  ├─ codex-ui/                # Codex 内节点界面
│  └─ local-service/           # 本地编排服务
├─ packages/
│  ├─ workflow-schema/         # 节点、边、工作流协议
│  ├─ node-editor/             # 画布和节点组件
│  ├─ agent-adapter/           # Agent Provider 与结构化输出
│  ├─ graph-engine/            # 图校验和拓扑排序
│  ├─ code-generator/          # IR 与代码生成
│  ├─ language-java/           # Java 解析、生成、编译与诊断适配器
│  ├─ runner/                  # 受控编译和运行
│  └─ diagnostics/             # 错误解析与节点映射
├─ examples/                   # 示例工作流
├─ tests/                      # 跨包集成与 E2E 测试
├─ docs/                       # 架构、协议和用户文档
├─ fixtures/                   # 编译错误及项目分析测试样本
└─ dist/                       # 版本化 Codex 插件发布包
```

发布包中只保留运行所需文件，不包含测试夹具、开发缓存、密钥、用户工作流或本机绝对路径。插件包必须能够在干净环境中依据清单完成加载，并能清楚报告缺少 JDK 21 或 Maven 条件。

## 11. 开工顺序清单

按以下顺序执行可以最快降低项目风险：

1. 先建立可安装、可打开、可卸载的最小 Codex 插件骨架。
2. 验证插件界面、本地 Java 服务、Codex Agent 和本地文件/进程权限边界。
3. 固化 Java 21 + Maven 基线以及 3 个端到端示例的验收结果。
4. 定义并评审工作流、节点、端口和 Agent 响应 schema。
5. 做画布、Agent 结构化输出、本地 Java 编译和错误解析四项技术验证。
6. 先打通“手写节点数据 → 生成 Java 代码 → 编译 → 错误定位”。
7. 再接入自然语言生成，避免同时调试 Agent 和编译链路。
8. 完成代码审查、确认、版本和回滚后，才允许实际执行。
9. 闭环稳定后再实现封装节点和项目分析。
10. 按 Codex 插件规范打包，并完成干净环境安装、升级和卸载测试。

## 12. 开工前必须确认的决策

发布形态已确定为 Codex 插件。以下技术边界不妨碍先搭建插件骨架，但必须在阶段 0 结束前确定：

1. 第一步插件支持哪个 Codex 最低版本和哪些操作系统？
2. Codex 插件页面、Agent 调用、本地文件和本地进程分别采用哪种官方扩展接口？
3. 首版是否严格固定 Java 21 + Maven，还是必须同时兼容 Java 17 或 Gradle？
4. Agent 使用 Codex 当前会话能力、单独 API 配置，还是允许本地模型？
5. 生成代码写入真实项目之前，是否必须逐文件确认？
6. 项目分析允许扫描的最大目录、文件数和文件大小是多少？
7. 是否允许自动安装依赖；若允许，需要怎样的用户授权？

在这些决策确认前，本文采用以下默认假设：发布为 Codex 插件、Windows 优先、Java 21 LTS + Maven Wrapper、普通 Java/JUnit 项目优先、优先复用 Codex 当前 Agent 能力、写入前确认、禁止自动安装依赖、仅分析用户明确选择的 Java 源代码目录。React + TypeScript 仅用于插件界面，不代表首版支持生成 TypeScript 业务代码。
